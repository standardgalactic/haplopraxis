   From Wikipedia, the free encyclopedia
   [76][330px-Hexdump_of_dev_urandom.png] 256 byte hex dump of
   /dev/urandom
   Pseudorandom number generator file in Unix-like operating systems

   In [77]Unix-like [78]operating systems, /dev/random
   and /dev/urandom are [79]special files that serve as
   [80]cryptographically secure pseudorandom number generators (CSPRNGs).
   They allow access to a [81]CSPRNG that is seeded with [82]entropy (a
   value that provides [83]randomness) from environmental noise, collected
   from [84]device drivers and other sources.^[85][1]
   /dev/random typically [86]blocked if there was less [87]entropy
   available than requested; more recently (see below for the differences
   between operating systems) it usually blocks at startup until
   sufficient entropy has been gathered, then unblocks permanently. The
   /dev/urandom device typically was never a blocking device, even if the
   pseudorandom number generator seed was not fully initialized with
   entropy since boot. Not all operating systems implement the same
   methods for
   /dev/random and /dev/urandom.

   This special file originated in Linux in 1994. It was quickly adopted
   by other Unix-like operating systems.^[88][2]

Linux

   [[89]edit]
   [90][330px-Rngtest_FIPS-140-2_screenshot.png] Rngtest testing
   /dev/random pool

   The Linux kernel provides the separate device files
   /dev/random and

   /dev/urandom. Since kernel version 5.6 of 2020, /dev/random only blocks
   when the CSPRNG hasn't initialized. Once initialized, /dev/random and
   /dev/urandom behave the same.^[91][3]

   In October 2016, with the release of [92]Linux kernel version 4.8, the
   kernel's
   /dev/urandom was switched over to a [93]ChaCha20-based
   [94]cryptographic pseudorandom number generator (CPRNG)
   implementation^[95][4] by [96]Theodore Ts'o, based on [97]Bernstein's
   well-regarded [98]stream cipher [99]ChaCha20.

   Since version 5.17 of the Linux kernel, the random number generator
   switched from using the [100]SHA-1 [101]cryptographic hash function in
   the entropy collector to [102]BLAKE2s, a newer, faster and more secure
   hash function.^[103][5]

Original implementation

   [[104]edit]

   Random number generation in [105]kernel space was implemented for the
   first time for [106]Linux^[107][2] in 1994 by [108]Theodore
   Ts'o.^[109][6] The implementation used [110]secure hashes rather than
   [111]ciphers,^[[112]clarification needed] to avoid [113]cryptography
   export restrictions that were in place when the generator was
   originally designed. The implementation was also designed with the
   assumption that any given hash or cipher might eventually be found to
   be weak, and so the design is durable in the face of any such
   weaknesses. Fast recovery from [114]pool compromise is not considered a
   requirement, because the requirements for pool compromise are
   sufficient for much easier and more direct attacks on unrelated parts
   of the operating system.

   In Ts'o's implementation, the generator keeps an estimate of the number
   of [115]bits of noise in the [116]entropy pool. From this entropy pool
   random numbers are created. When read, the
   /dev/random device will only return random bytes within the estimated
   number of bits of noise in the entropy pool. When the entropy pool is
   empty, reads from /dev/random will [117]block until additional
   environmental noise is gathered.^[118][7] The intent is to serve as a
   [119]cryptographically secure pseudorandom number generator, delivering
   output with entropy as large as possible. This is suggested by the
   authors for use in generating cryptographic keys for high-value or
   long-term protection.^[120][7]

   A counterpart to
   /dev/random is /dev/urandom ("unlimited"^[121][8]/non-blocking random
   source^[122][7]) which reuses the internal pool to produce more
   pseudo-random bits. This means that the call will not block, but the
   output may contain less entropy than the corresponding read from
   /dev/random. While /dev/urandom is still intended as a pseudorandom
   number generator suitable for most cryptographic purposes, the authors
   of the corresponding [123]man page note that, theoretically, there may
   exist an as-yet-unpublished attack on the algorithm used by
   /dev/urandom, and that users concerned about such an attack should use
   /dev/random instead.^[124][7] However such an attack is unlikely to
   come into existence, because once the entropy pool is unpredictable it
   doesn't leak security by a reduced number of bits.^[125][9]

   It is also possible to write to
   /dev/random. This allows any user to mix random data into the pool.
   Non-random data is harmless, because only a privileged user can issue
   the [126]ioctl needed to increase the entropy estimate.^[[127]dubious –
   [128]discuss] The current amount of entropy and the size of the Linux
   kernel entropy pool, both measured in bits, are available in
   /proc/sys/kernel/random/ and can be displayed by the command cat
   /proc/sys/kernel/random/entropy_avail and cat
   /proc/sys/kernel/random/poolsize respectively.

Entropy injection

   [[129]edit]

   Gutterman, Pinkas, & Reinman in March 2006 published a detailed
   cryptographic analysis of the Linux random number generator^[130][10]
   in which they describe several weaknesses. Perhaps the most severe
   issue they report is with [131]embedded or [132]Live CD systems, such
   as routers and [133]diskless clients, for which the bootup state is
   predictable and the available supply of entropy from the environment
   may be limited. For a system with non-volatile memory, they recommend
   saving some state from the RNG at shutdown so that it can be included
   in the RNG state on the next reboot. In the case of a router for which
   network traffic represents the primary available source of entropy,
   they note that saving state across reboots "would require potential
   attackers to either eavesdrop on all network traffic" from when the
   router is first put into service, or obtain direct access to the
   router's internal state. This issue, they note, is particularly
   critical in the case of a wireless router whose network traffic can be
   captured from a distance, and which may be using the RNG to generate
   keys for data encryption.

   The Linux kernel provides support for several [134]hardware random
   number generators, should they be installed. The raw output of such a
   device may be obtained from
   /dev/hwrng.^[135][11]

   With Linux kernel 3.16 and newer,^[136][12] the kernel itself mixes
   data from [137]hardware random number generators into
   /dev/random on a sliding scale based on the definable entropy
   estimation quality of the HWRNG. This means that no userspace daemon,
   such as rngd from rng-tools, is needed to do that job. With Linux
   kernel 3.17+, the VirtIO RNG was modified to have a default quality
   defined above 0,^[138][13] and as such, is currently the only HWRNG
   mixed into /dev/random by default.

   The entropy pool can be improved by programs like
   timer_entropyd, haveged, randomsound etc. With rng-tools, [139]hardware
   random number generators like Entropy Key, etc. can write to
   /dev/random. The [140]diehard tests programs diehard, dieharder and ent
   can test these random number
   generators.^[141][14]^[142][15]^[143][16]^[144][17]

   causing the first four bits of the RNG output to be 0. This is possible
   because Linux reseeds H on an ongoing basis instead of using a single
   high quality seed.^[148][18]

   Bernstein also argues that entropy injection is pointless once the
   CSPRNG has been initialized.^[149][18]

   In kernel 5.17 (backported to kernel 5.10.119), Jason A. Donenfeld
   offered a new design of the Linux entropy pool infrastructure.
   Donenfeld reported that the old pool, consisting of a single 4096-bit
   [150]LFSR is vulnerable to two attacks: (1) an attacker can undo the
   effect of a known input; (2) if the whole pool's state is leaked, an
   attacker can set all bits in the pool to zero. His new design, which is
   faster and safer, uses the blake2s hash function for mixing a 256-bit
   pool.^[151][19]

BSD systems

   [[152]edit]

   The [153]FreeBSD operating system provides a
   /dev/urandom link to /dev/random. Both block only until properly
   seeded. FreeBSD's PRNG ([154]Fortuna) reseeds regularly, and does not
   attempt to estimate entropy. On a system with small amount of network
   and disk activity, reseeding is done after a fraction of a
   second.^[155][20]

   [156]DragonFly BSD inherited FreeBSD's random device files when it was
   forked.^[157][21]^[[158]non-primary source needed]^[159][22]

   Since [160]OpenBSD 5.1 (May 1, 2012)
   /dev/random and /dev/arandom uses [161]arc4random, a CSPRNG function
   based on [162]RC4. The function was changed to use the stronger
   [163]ChaCha20 with OpenBSD 5.5 (May 1, 2014). The system automatically
   uses hardware random number generators (such as those provided on some
   Intel PCI hubs) if they are available, through the [164]OpenBSD
   Cryptographic Framework.^[165][23]^[166][24] /dev/arandom was removed
   in OpenBSD 6.3 (April 15, 2018).^[167][25]

   [168]NetBSD's implementation of the legacy arc4random() API has been
   switched over to ChaCha20 as well.^[169][26]

macOS, iOS and other Apple OSes

   [[170]edit]

   All Apple OSes have moved to Fortuna since at least December 2019,
   possibly earlier.^[171][27] It is based on [172]SHA-256. Multiple
   entropy sources such as the secure enclave RNG, boot phase timing
   jitter, hardware interrupt (timing assumed) are used. RDSEED/RDRAND is
   used on Intel-based Macs that support it. Seed (entropy) data is also
   stored for subsequent reboots.

   Prior to the change, [173]macOS and [174]iOS used 160-bit [175]Yarrow
   based on [176]SHA-1.^[177][28]

   There is no difference between
   /dev/random and /dev/urandom; both behave
   identically.^[178][29]^[179][30]

Other operating systems

   [[180]edit]

   /dev/random and /dev/urandom are also available on Solaris,^[181][31]
   NetBSD,^[182][32] Tru64 UNIX 5.1B,^[183][33] AIX 5.2^[184][34] and
   HP-UX 11i v2.^[185][35] As with FreeBSD, AIX implements its own
   Yarrow-based design, however AIX uses considerably fewer entropy
   sources than the standard /dev/random implementation and stops
   refilling the pool when it thinks it contains enough entropy.^[186][36]

   In [187]Windows NT, similar functionality is delivered by
   ksecdd.sys, but reading the special file \Device\KsecDD does not work
   as in UNIX. The documented methods to generate cryptographically random
   bytes are [188]CryptGenRandom and [189]RtlGenRandom. Windows
   [190]PowerShell provides access to a cryptographically secure
   pseudorandom number generator via the Get-SecureRandom
   cmdlet.^[191][37]

   [192]Cygwin on Windows provides implementations of both
   /dev/random and /dev/urandom, which can be used in scripts and
   programs.^[193][38]
