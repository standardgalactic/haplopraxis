   (Redirected from [60]/usr)
   Directory structure used by a Unix-like operating system
   "Usr" redirects here. For other uses, see [61]USR.
   "Unix file system" redirects here. For UFS, a specific file system used
   by many Unix and Unix-like operating systems, see [62]Unix File System.
   [63][220px-Version_7_UNIX_SIMH_PDP11_Filesystem_Layout.png] [64]Version
   7 Unix filesystem layout: subdirectories of "/" and
   "/usr"[65][220px-Standard-unix-filesystem-hierarchy.svg.png] An
   overview of a [66]Unix filesystem layout

   In [67]Unix and [68]operating systems inspired by it, the [69]file
   system is considered a central component of the operating
   system.^[70][1] It was also one of the first parts of the system to be
   designed and implemented by [71]Ken Thompson in the first experimental
   version of Unix, [72]dated 1969.^[73][2]

   As in other operating systems, the filesystem provides information
   storage and retrieval, and one of several forms of [74]interprocess
   communication, in that the many small programs that traditionally form
   a Unix system can store information in files so that other programs can
   read them, although [75]pipes complemented it in this role starting
   with the [76]Third Edition. Also, the filesystem provides access to
   other resources through so-called [77]device files that are entry
   points to [78]terminals, [79]printers, and [80]mice.

   The rest of this article uses Unix as a [81]generic name to refer to
   both the original Unix operating system and its many [82]workalikes.

Principles

   [[83]edit]

   The filesystem appears as one [84]rooted tree of directories.^[85][1]
   Instead of addressing separate volumes such as [86]disk partitions,
   removable media, and [87]network shares as separate trees (as done in
   [88]DOS and [89]Windows: each drive has a drive letter that denotes the
   root of its file system tree), such volumes can be [90]mounted on a
   directory, causing the volume's file system tree to appear as that
   directory in the larger tree.^[91][1] The root of the entire tree is
   denoted /.

   In the original [92]Bell Labs Unix, a two-disk setup was customary,
   where the first disk contained startup programs, while the second
   contained users' files and programs. This second disk was mounted at
   the empty directory named usr on the first disk, causing the two disks
   to appear as one filesystem, with the second disk’s contents viewable
   at /usr.

   Unix directories do not contain files. Instead, they contain the names
   of files paired with references to so-called [93]inodes, which in turn
   contain both the file and its [94]metadata (owner, permissions, time of
   last access, etc., but no name). Multiple names in the file system may
   refer to the same file, a feature termed a [95]hard link.^[96][1] The
   mathematical traits of hard links make the file system a limited type
   of [97]directed acyclic graph, although the directories still form a
   tree, as they typically may not be hard-linked. (As originally
   envisioned in 1969, the Unix file system would in fact be used as a
   general graph with hard links to directories providing navigation,
   instead of path names.^[98][2])

File types

   [[99]edit]
   Main article: [100]Unix file types

   The original Unix file system supported three types of files: ordinary
   files, [101]directories, and "special files", also termed device
   files.^[102][1] The [103]Berkeley Software Distribution (BSD) and
   [104]System V each added a file type to be used for [105]interprocess
   communication: BSD added [106]sockets,^[107][3] while System V added
   [108]FIFO files.

   BSD also added [109]symbolic links (often termed "symlinks") to the
   range of file types, which are files that refer to other files, and
   complement hard links.^[110][3] Symlinks were modeled after a similar
   feature in [111]Multics,^[112][4] and differ from hard links in that
   they may span filesystems and that their existence is independent of
   the target object. Other Unix systems may support additional types of
   files.^[113][5]

Conventional directory layout

   [[114]edit]

   Certain conventions exist for locating some kinds of files, such as
   programs, system configuration files, and users' [115]home directories.
   These were first documented in the hier(7) [116]man page since
   [117]Version 7 Unix;^[118][6] subsequent versions, derivatives and
   clones typically have a similar man
   page.^[119][7]^[120][8]^[121][9]^[122][10]^[123][11]^[124][12]

   The details of the directory layout have varied over time. Although the
   file system layout is not part of the [125]Single UNIX Specification,
   several attempts exist to standardize (parts of) it, such as the
   [126]System V [127]Application Binary Interface, the [128]Intel Binary
   Compatibility Standard, the Common Operating System Environment, and
   [129]Linux Foundation's [130]Filesystem Hierarchy Standard
   (FHS).^[131][13]

   Here is a generalized overview of common locations of files on a Unix
   operating system:
   Directory or file Description
   / The slash / character alone denotes the root of the filesystem tree.

          /bin

   Stands for [132]binaries and contains certain fundamental utilities,
   such as ls or cp, that are needed to mount /usr, when that is a
   separate filesystem, or to run in one-user (administrative) mode when
   /usr cannot be mounted. In System V.4, this is a symlink to /usr/bin.
   Otherwise, it needs to be on the root filesystem itself.

          [133]/boot

   Contains all the files needed for successful booting process. In
   [134]Research Unix, this was one file rather than a
   directory.^[135][14] Nowadays usually on the root filesystem itself,
   unless the system, bootloader etc. require otherwise.

          [136]/dev

   Stands for devices. Contains [137]file representations of peripheral
   devices and [138]pseudo-devices. See also: [139]Linux Assigned Names
   and Numbers Authority. Needs to be on the root filesystem itself.

          /etc

   Contains system-wide configuration files and system databases; the name
   stands for [140]et cetera^[141][14] but now a better expansion is
   editable-text-configurations. Originally also contained "dangerous
   maintenance utilities" such as init,^[142][6] but these have typically
   been moved to /sbin or elsewhere. Needs to be on the root filesystem
   itself.

          /home

   Contains user home directories on Linux and some other systems. In the
   original version of Unix, home directories were in /usr
   instead.^[143][15] Some systems use or have used different locations
   still: [144]macOS has home directories in /Users, older versions of BSD
   put them in /u, [145]FreeBSD has /usr/home.

          /lib

   Originally essential libraries: [146]C libraries, but not [147]Fortran
   ones.^[148][14] On modern systems, it contains the shared libraries
   needed by programs in /bin, and possibly [149]loadable kernel module,
   [150]device drivers or [151]binary blobs. Linux distributions may have
   variants /lib32 and /lib64 for multi-architecture support.

          /media

   Default mount point for removable devices, such as USB sticks, media
   players, etc. By common sense, the directory itself, whose
   subdirectories are mountpoints, is on the root partition itself.

          /mnt

   Stands for mount. Empty directory commonly used by system
   administrators as a temporary mount point. By common sense, the
   directory itself, whose subdirectories are mountpoints, is on the root
   partition itself.

          /opt

   Contains locally installed software. Originated in [152]System V, which
   has a [153]package manager that installs software to this directory
   (one subdirectory per package).^[154][16]

          /proc

   [155]procfs virtual [156]filesystem showing information about
   [157]processes as files.

          /root

   The home directory for the [158]superuser root - that is, the system
   administrator. This account's home directory is usually on the initial
   filesystem, and hence not in /home (which may be a mount point for
   another filesystem) in case specific maintenance needs to be performed,
   during which other filesystems are not available. Such a case could
   occur, for example, if a hard disk drive suffers failures and cannot be
   properly mounted.

          /sbin

   Stands for "[159]system (or superuser) binaries" and contains
   fundamental utilities, such as init, usually needed to start, maintain
   and recover the system. Needs to be on the root partition itself.

          /srv

   Server data (data for services provided by system).

          /sys

   In some [160]Linux distributions, contains a [161]sysfs virtual
   [162]filesystem, containing information related to hardware and the
   operating system. On BSD systems, commonly a symlink to the kernel
   sources in /usr/src/sys.

          /tmp

   A place for temporary files not expected to survive a reboot. Many
   systems clear this directory upon startup or use [163]tmpfs to
   implement it.

          /unix

   The Unix [164]kernel in Research Unix and [165]System V.^[166][14] With
   the addition of [167]virtual memory support to [168]3BSD, this got
   renamed /vmunix.

          /usr

   The "user file system": originally the directory holding user home
   directories,^[169][15] but already by the Third Edition of
   [170]Research Unix, ca. 1973, reused to split the operating system's
   programs over two disks (one of them a 256K fixed-head drive) so that
   basic commands would either appear in /bin or /usr/bin.^[171][17] It
   now holds executables, libraries, and shared resources that are not
   system critical, such as the [172]X Window System, [173]window
   managers, [174]scripting languages, etc. In older Unix systems, user
   home directories might still appear in /usr alongside directories
   containing programs, although by 1984 this depended on local
   customs.^[175][14]

                /usr/include

   Stores the development headers used throughout the system. [176]Header
   files are mostly used by the #include directive in [177]C language,
   which historically is how the name of this directory was chosen.

                /usr/lib

   Stores the needed libraries and data files for programs stored within
   /usr or elsewhere.

                /usr/libexec

   Holds programs meant to be executed by other programs rather than by
   users directly. E.g., the [178]Sendmail executable may be found in this
   directory.^[179][18] Not present in the FHS until 2011;^[180][19] Linux
   distributions have traditionally moved the contents of this directory
   into /usr/lib, where they also resided in 4.3BSD.

                /usr/local

   Resembles /usr in structure, but its subdirectories are used for
   additions not part of the operating system distribution, such as custom
   programs or files from a [181]BSD [182]Ports collection. Usually has
   subdirectories such as /usr/local/lib or /usr/local/bin.

                /usr/share

   Architecture-independent program data. On Linux and modern BSD
   derivatives, this directory has subdirectories such as man for
   [183]manpages, that used to appear directly under /usr in older
   versions.

          /var

   Stands for variable. A place for files that might change frequently -
   especially in size, for example e-mail sent to users on the system, or
   process-ID [184]lock files.

                /var/log

   Contains system log files.

                /var/mail

   The place where all incoming mail is stored. Users (other than root)
   can access their own mail only. Often, this directory is a
   [185]symbolic link to /var/spool/mail.

                /var/spool

   [186]Spool directory. Contains print jobs, mail spools and other queued
   tasks.

                /var/src

   The place where the uncompiled source code of some programs is.

                /var/tmp

   The /var/tmp directory is a place for temporary files which should be
   preserved between system reboots.
